# Nexora TMS — P0/P1 Audit Update

Date: 2026-09-11

## Confirmed controls

- Tenant context is request-scoped and immutable after establishment.
- Tenant selection requires an authenticated principal and an active membership in the selected tenant.
- Database tenant/user/integration context is installed with `set_config(..., true)` inside a transaction.
- Core Freight, IAM, commercial terms, capacity assignment and asynchronous persistence schemas use tenant-scoped RLS policies and composite tenant-aware foreign keys.
- Commercial terms enforce non-negative monetary values, approval metadata consistency and optimistic version storage.
- Outbox and durable jobs implement tenant-scoped idempotency keys and durable retry/lease state.

## P1 findings and remediation status

1. **Neon topology mismatch — mitigated for the new project.** The new Nexora Neon project is `morning-grass-06967990`. Dedicated `development` and `production` branches now exist and are ready. Legacy workflows that reference `raspy-river-76339604` must still be migrated explicitly before they are allowed to target the new project.
2. **Process-local API rate limiting — open.** The current limiter remains in-memory and must be complemented by a distributed control before horizontal production scaling.
3. **Chunked request body limits — partially remediated.** JSON and URL-encoded request parsers now enforce `MAX_REQUEST_BODY_BYTES`, covering chunked requests for those media types. Multipart uploads still require an explicit streaming/upload adapter limit.
4. **Content-Type validation — remediated in PR.** Media types are parsed and compared exactly, while parameters such as JSON charset and multipart boundaries remain supported. Prefix-spoofing cases are covered by regression tests.
5. **Finance/payment idempotency contract — open.** Persistence has tenant-scoped idempotency support for durable jobs/outbox, but an explicit API-level payment idempotency contract remains required before production finance operations.

## Safety status

No production application migration was applied. The `production` and `development` branches were created from the current Nexora `main` branch for topology validation. Application security changes remain isolated in PR #4 until CI and review are complete.
