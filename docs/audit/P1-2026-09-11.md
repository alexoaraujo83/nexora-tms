# Nexora TMS — P0/P1 Audit Update

Date: 2026-09-11

## Confirmed controls

- Tenant context is request-scoped and immutable after establishment.
- Tenant selection requires an authenticated principal and an active membership in the selected tenant.
- Database tenant/user/integration context is installed with `set_config(..., true)` inside a transaction.
- Core Freight, IAM, commercial terms, capacity assignment and asynchronous persistence schemas use tenant-scoped RLS policies and composite tenant-aware foreign keys.
- Commercial terms enforce non-negative monetary values, approval metadata consistency and optimistic version storage.
- Outbox and durable jobs implement tenant-scoped idempotency keys and durable retry/lease state.

## P1 findings

1. Neon CI workflows reference legacy project `raspy-river-76339604` while the new Nexora project is `morning-grass-06967990`. The workflow also assumes a `production` branch topology that has not yet been established in the new project. Do not execute the legacy migration/topology workflows against the new project until topology is deliberately created and validated.
2. API rate limiting is process-local/in-memory. It is not sufficient as the sole distributed abuse-control mechanism when API instances scale horizontally.
3. API payload-size protection primarily relies on `Content-Length`; chunked requests require explicit streaming/body-parser enforcement.
4. Content-Type validation should use strict media-type parsing rather than permissive prefix matching.
5. Finance/commercial persistence contains versioning and approval invariants, but a repository-wide explicit `idempotency_key` search did not find an API-level payment idempotency contract. This remains a validation item before production finance operations.

## Safety status

No production migration was applied. The new Neon database remains isolated for validation. Changes in this document are audit documentation only.
